# `#[class]` macro implementation design

Related specification: [`../../specs/macro_class_spec.md`](../../specs/macro_class_spec.md). Implementation invariants for agents are in [`../../agents/class-model.md`](../../agents/class-model.md).

## Expansion model

The macro parses the class declaration and paired implementation, validates the public class contract, then emits the concrete storage type, extension trait implementation, ancestor forwarding machinery, constructors, and generated accessors required by that contract.

Ordinary and root classes generate their own extension trait surface. `trait_only` declares an interface without concrete storage. `struct_only` implements an existing trait for concrete storage and therefore cannot add the same per-class forwarding surface as an ordinary class.

View components that are lowered into a generated `#[class]` implementation pass their companion
`#[overridable]`/`#[overrides]` method metadata through this same expansion boundary. The class macro
remains the single owner of ancestor forwarding and runtime virtual dispatch; component codegen does
not create a parallel vtable, forwarding table, or method-name-specific route.

## Ancestor forwarding

Generated `__elwindui_inherit_*!` macros carry the ancestor chain across module and crate boundaries. `#[overridable]` emits dynamic accessors used by forwarding; `#[overrides]` routes through the subclass implementation. Sealed members omit the override route.

**`struct_only` transparency (Issue #128)**: a `struct_only` implementor of a class-managed interface (an interface generated by `trait_only`, ordinary, or root class mode) is a fully transparent bridge for that interface's `#[overridable]`/`#[overrides]` contract, at arbitrary ordinary-descendant depth, across real crate boundaries. Previously (CI-8 of the elwindui #80 lifecycle-refactor tracking issue, `docs/design/runtime/component_lifecycle_design.md` §4g) this did not work — an `#[overridable]` method declared on a `trait_only` interface was not recognized as an available override slot by an ordinary class that `inherits` a `struct_only` implementor of that interface — worked around at that one call site (`Window::show`/`hide`/`close`) with a plain inherent method reached via UFCS instead of the override-chain machinery. `macro_class_spec.md` still documents that `struct_only` cannot *declare* new overridable slots of its own; #128's fix is the separate mechanism that lets an *ancestor's* overridable declaration reach arbitrarily far down through a `struct_only` link.

Root cause: `trait_only`'s own expansion previously read only each method's `syn::Signature`, never its `syn::Attribute`s, when building the interface's `{Name}Ext` trait — an `#[overridable]` attribute was silently discarded at that point, so no downstream consumer (same-crate or cross-crate) could ever see it. Independently, a `struct_only` class's own generated descendant-facing macros were built purely from that `struct_only` block's own locally-known `#[overridable]` tags (almost always empty), with no path to consult the interface it implements.

Fix — a generated class-interface bridge macro: every class-managed interface (`trait_only`, ordinary, root) generates a hidden `__elwindui_class_interface_<ClassName>!` macro, re-exported through its own `__elwindui_class_interface_macros_of_<bare_name>` wrapper module (`class_interface_wrapper_mod_ident` — the same naming scheme for all three shapes, not a second convention invented for ordinary/root). The bridge has two arms:

- `@impl_struct_only_members $ExtTrait:path, has_matching_base = [..]` — invoked directly (item position) by a forwardable `struct_only` implementor's own expansion, spliced *inside* an `impl` header the `struct_only` class's own `expand_impl` still builds and owns itself (`impl #impl_generics $ExtTrait for $StructTy #ty_generics #where_clause { #bridge_path!(@impl_struct_only_members $ExtTrait, has_matching_base = [..]); #(#bodies)* }`). Emits the ordinary shared `__dyn_x` accessor plus one *reflexive* per-method accessor for every `#[overridable]` slot the interface declares (baked in at the interface's own compile time — a `struct_only` block never re-discovers or duplicates this list) — members only, never the outer `impl` header itself (PR #164 review finding A3: an earlier revision let the bridge own the whole header, silently dropping a generic `struct_only<T>`'s own `impl_generics`/`ty_generics`/`where_clause`). `has_matching_base = [..]` (PR #164 final remediation round, finding C2) is `[$RootConcrete:path]`/`[]`, supplied by the caller from its own already-fully-qualified `inherits = ..` argument text (`struct_only_matches_direct_parent`) — see the root-mode paragraph below for what it drives; a non-root interface's own bridge arm simply ignores it.
- `@inherit_through_struct_only $SubType:ty, $OwnTrait:path, $OwnConcrete:path, $RootConcrete:path; $($overrides:tt)*` — a forwardable `struct_only` class's own entry macro (`__elwindui_inherit_<Name>!`) redirects its body here instead of classifying against its own (empty) `overridable_names`. This arm forwards, unexamined, into the interface's real entry macro (`$crate`-self-referenced, always same-crate relative to the bridge's own definition) — reusing the *existing* recursive classify muncher exactly as an ordinary `inherits = ..` chain would. Arbitrary further descendant depth (`C -> D -> E -> ..`) falls out of that existing recursion with no depth-specific code added anywhere. `$RootConcrete` (finding C2) travels alongside `$OwnConcrete` starting here — see the root-mode paragraph below for why the two must be tracked separately once a bridge hop is involved.

**Ancestor-trait resolution — `__ElwindUIOwnExt` (PR #164 review finding A2)**: every class-managed ancestor's own `macro_reexport_mod_ident` wrapper module (`__elwindui_macros_of_<bare_name>`) additionally exposes a stable hidden alias, `pub use <target> as __ElwindUIOwnExt;`, where `<target>` is that class's own real `{ClassName}Ext` trait (ordinary/root) or its `struct_only = ..Ext` target verbatim (`struct_only`). `ancestor_own_trait` (consulted by every descendant's own supertrait bound and recursion target) resolves purely through this alias — `<ancestor's own module prefix>::__ElwindUIOwnExt` — never through a same-crate registry lookup or a `{ConcreteName}Ext` naming-convention guess from the ancestor's own bare name. This replaced an earlier revision's registry-based resolution, which broke for a same-crate `struct_only` implementor whose own bare name doesn't happen to match the interface it implements (the established `Window`/`NativeControl` convention is not a language guarantee) and required a manually-authored `{ConcreteName}Ext` compatibility alias as a workaround — no such alias is written or needed anywhere in the codebase now. Generic reattachment (a descendant's own `inherits = Parent<Concrete>` trailing type arguments, which a plain `use` cannot itself carry) only applies when the alias is generic-parallel to the ancestor struct itself (ordinary/root's own `{ClassName}Ext<T>`) — never for a `struct_only` ancestor's alias, whose target is an independently-declared, non-generic interface path.

Path resolution for the bridge itself follows the same discipline the rest of this mechanism already requires — computed fresh by each caller from information *it* reliably holds (its own `inherits = ..` argument text, reached through the target's existing wrapper module — `path_module_prefix`/`class_interface_wrapper_mod_ident`), never baked once into a macro body that later gets re-expanded from an arbitrary third crate.

`class_interface_wrapper_mod_ident`'s module is deliberately *not* the same `__elwindui_macros_of_<bare_name>` module (`macro_reexport_mod_ident`) a class's own entry/skip/classify trio (and now `__ElwindUIOwnExt`) live in — a `struct_only` implementor of the same bare name, in a different crate, also generates its own `macro_reexport_mod_ident` module for itself (e.g. `elwindui-core`'s `trait_only Window` and each backend's own `struct_only Window` deliberately share the bare name "Window" — see this file's own top doc comment); reusing one module name for both would collide when a facade crate glob-merges both crates' top-level items together.

`no_ancestor_forward` targets (hand-written traits predating the `__dyn_x` convention) are untouched by any of this — the bridge is never generated for them and never consulted.

**Registry-independent generic reattachment — `__ElwindUIOwnExtBound`/`__elwindui_apply_own_ext` (PR #164 final remediation round, finding A5)**: whether a descendant's own `inherits = Ancestor<Args>` trailing generic arguments must be reattached onto the ancestor's own `{Name}Ext` trait depends on the ancestor's *shape* (ordinary/root vs. forwardable `struct_only`) — reattach for a generic ordinary/root ancestor (`ParentExt<T>`), never reattach for a generic `struct_only` implementor of a non-generic interface (the real interface stays `SomeIfaceExt`, never `SomeIfaceExt<ConcreteType>`). An earlier revision decided this via a same-crate registry (`same_crate_classes`), which is empty in a separate `cargo build` process and so cannot work cross-crate — replaced by two proc-macro-time/macro-expansion-time mechanisms, split because Rust does not permit a macro invocation in supertrait-bound position (`trait X: some_macro!() {}` is a hard parse error), so a single macro-protocol (as an early draft of this fix assumed) cannot cover both call sites:
- **Bound position** (a descendant's own supertrait bound): every class-managed ancestor generates `__ElwindUIOwnExtBound_<bare_name>`, a `#[doc(hidden)]` wrapper trait declared with *exactly* the ancestor's own generic parameter list, supertrait-bound to the ancestor's real `{Name}Ext` trait, satisfied via a blanket impl over *any* type implementing that real trait (not a narrow impl for just the declaring struct — a multi-hop descendant like `Shape`/`Control` also implements `UIElementExt` without literally being `UIElement`). A descendant's own bound resolves through this wrapper (`ancestor_own_trait_bound`), which — being an ordinary trait, not a macro — participates in bound position exactly as ordinary Rust generics resolution expects.
- **Dispatch-routing position** (whether to pass a descendant's own concrete generic-argument tokens further down the recursion): every class-managed ancestor also generates `__elwindui_apply_own_ext_<bare_name>`, a macro-expansion-time policy macro with exactly two possible bodies baked in at the ancestor's own generation time — ordinary/root echoes the caller's concrete generic-argument tokens back; forwardable `struct_only` discards them. Each recursion step generates a fresh, uniquely-named continuation macro that already has everything else baked in, receiving only the policy macro's resolved tokens and splicing them into the final entry-macro invocation.

Neither mechanism ever inspects `same_crate_classes`/any other same-crate-only registry, and neither ever globally appends or drops generic arguments independent of the specific ancestor being recursed through.

**Recursive forwarding also uses the dispatch-routing policy — `AncestorRoute` (PR #164 final remediation round, finding A6)**: A5's fix above only covers the *immediate* `inherits = ..` edge (`expand_impl`'s own prelude, resolved once per class, at that class's own generation time). But `build_inherit_macros` generates classify/skip macros that are *reused* for every future descendant depth — when class `D` (`inherits = Concrete<T>`) has its own classify muncher's base case fire for some later descendant `E` (`inherits = D`), that base case needs to forward *past* `D` into `Concrete`'s own real interface, and an earlier revision still baked that resolved trait as a literal token there too, via the same same-crate-registry heuristic A5 replaced for the immediate hop — correct only when `Concrete` happened to be in the same crate as `D`, wrong for any `struct_only`/generic ancestor beyond that. Fixed by extending A5's own protocol to the recursive case: `build_ancestor_route` builds an `AncestorRoute` (deliberately unresolved — `own_ext_prefix`/`concrete_args`/`concrete`/`bridge_path`/`policy_path`, all `rewrite_crate_segment`-treated) in place of the old `(next_trait, next_concrete, next_bridge_path)` tuple; `build_inherit_macros` uses it to generate one fixed, once-per-class continuation macro (`__elwindui_continue_recursive_inherits_of_<bare_name>`, generated *once* per class regardless of how many future descendants eventually reach it — a per-invocation name would collide the second time a different descendant reaches the same hop), which `skip_ident`'s and classify's own base-case bodies invoke through `Concrete`'s own `__elwindui_apply_own_ext_*!` policy macro (extended with a second arm accepting `$SubType`/trailing override tokens alongside the continuation path, since those are only known once a real descendant chain actually reaches this hop — not at `D`'s own proc-macro time). `ancestor_own_trait`/`struct_only_ancestor_in_this_crate` (the old registry-dependent resolution these replaced) are deleted entirely, not merely superseded — no valid non-semantic caller remained. Regression coverage: `crates/elwindui/tests/class_bridge_cross_crate.rs`'s `BridgeFixtureGenericDeepDerived` (a *second* ordinary hop below a generic `struct_only` bridge, T19) and `GenericOrdinaryDeepDerived` (a *second* hop below a generic ordinary ancestor, T20), plus a macro-expansion-level test (`class.rs`'s own `recursive_forwarding_metadata_uses_the_next_ancestors_own_policy_macro`, T21) proving the generated recursive metadata calls the policy macro rather than embedding a resolved trait.

**Root-mode `struct_only` support (PR #164 final remediation round, finding C2)**: a root class (no `inherits` at all, e.g. `UIElement`) generates its own bridge macro too (proven at the macro-expansion level, `crates/elwindui-macros/src/class.rs`'s own test module). An earlier revision concluded that no *runtime* `struct_only` implementor of a root interface was achievable, since root mode's own `as_ui_element(&self) -> &Self` is a required trait method whose return type is hard-pinned to the declaring root struct's own concrete type — that conclusion is superseded: it *is* achievable, by requiring the `struct_only` implementor to *also* `inherits = <the same root class>`, composing the real root storage (`self.base`) and forwarding `as_ui_element` to it (`self.base.as_ui_element()`). `as_ui_element`'s own signature is unchanged — still a concrete, hard-pinned return type, never `&dyn RootExt` or an associated root-storage type; the composition, not a redesign of the accessor, is what makes this work. `struct_only_matches_direct_parent` (purely syntactic — stringified comparison of the class's own `struct_only=`/`inherits=` attribute text, no registry) decides, at the `struct_only` implementor's own compile time, whether its `inherits=` genuinely names the matching root class; the result becomes `has_matching_base`, threaded into `@impl_struct_only_members` as described above. A non-matching (or absent) `inherits` produces a dedicated `compile_error!` instead of a raw `E0609`/`E0053` once the missing method is eventually discovered by the compiler. The root's own concrete path can never be baked as a literal token into the bridge macro's body (it is `#[macro_export]`'d and invoked from whatever crate/module declares the `struct_only` implementor, essentially never the root class's own defining module, and a proc-macro has no `module_path!()`-equivalent to compute the real one) — it travels as the `$RootConcrete` macro parameter instead, supplied fresh by the `struct_only` caller from its own already-fully-qualified `inherits=` text. `$RootConcrete` differs from `$OwnConcrete` once a bridge hop is involved (`$OwnConcrete` stays the `struct_only` implementor's own concrete type throughout, matching what its own reflexive named accessor returns; `$RootConcrete` is recomputed at each bridge hop to the actual root type) — a distinction invisible in a normal, non-bridged chain, where both values always coincide transitively. Runtime coverage: `elwindui-core::ui::testsupport`'s `BridgeRootBase` -> `BridgeRootConcrete` -> `BridgeRootDerived` (same-crate) and `crates/elwindui/tests/class_bridge_cross_crate.rs`'s `BridgeFixtureRoot` -> `BridgeFixtureRootConcrete` -> `BridgeFixtureRootDerived` (cross-crate).

Generated macros use fully qualified paths. `$crate` is retained where it must refer to the declaring crate; tokens that intentionally refer to the consuming crate are rewritten during expansion.

## Construction

`construct` is the single source for constructor arguments. Expansion generates `new`, initializes the weak self handle after allocation, and invokes `on_constructed` only after the object can be safely upgraded through that handle.

Expansion also generates a second, unconditional constructor, `__new_unmounted` (CI-7 of the elwindui #80 lifecycle-refactor tracking issue, `docs/design/runtime/component_lifecycle_design.md` §4f) — the same allocation step as `new`, without the trailing `on_constructed` invocation. It exists so a caller (today, only `EnvironmentScope`'s own generated code) can construct an object and then call `mount(environment)` on it explicitly, against a specific `EnvironmentContext`, instead of letting construction auto-mount it. Both constructors are always emitted together; there is no class-level flag selecting one or the other, because the choice belongs to the call site, not the type.

Hand-written `new` or `__new_unmounted` is rejected because either would compete with the generated ownership sequence.

## Registry and analysis

Cross-item class information is stored in a compilation-scoped registry keyed so separate consuming crates cannot contaminate one another. Source-order dependencies are minimized, but rust-analyzer may expand incomplete files in an order unavailable to normal rustc.

The rust-analyzer shadow expansion supplies enough generated structure for name resolution without changing rustc output. Spans from user declarations are preserved on generated public items and forwarding calls where possible so diagnostics and breakpoints point back to source.

## Shape macro protocol (`__elwindui_props_*!`)

Every class also emits a `__elwindui_props_{Name}!` declarative macro carrying its DSL-visible property surface across the same crate boundary `__elwindui_inherit_*!` carries the ancestor chain across (`elwindui-codegen` never has a local `TypeInfo` for a real builtin — only a same-crate DSL fixture in tests does — so it constructs against this macro instead of a registry entry). Each query is a two-hop `@x`/`@x_from` pair: the entry seeds `$origin` with this class's own name and hands off to the `_from` form, which either matches a literal per-property arm or forwards unmatched names to the parent's own macro, unchanged, so `$origin` still names the type the use site actually wrote by the time a terminal `compile_error!` or catch-all is reached.

- `@set`/`@set_from` — assigns a plain (non-attached, non-collection-content) property, via `wrap_prop_value`'s per-property conversion (a `String` gets `&`, `Brush`/`Color` gets `.into()` plus a declared-type-driven `Some(..)`, a plain type passes through unchanged).
- `@set_with_environment`/`@set_with_environment_from` — assigns a property while carrying the node's effective `EnvironmentContext`. A `#[prop(semantic_brush, ..)]` arm resolves `BrushStyle` and maps `PlatformDefault` to `@clear`; an ordinary property delegates to `@set` unchanged. `#[text_style]` contributes equivalent arms for its injected fields, with only `foreground` marked semantic.
- `@is_semantic_brush`/`@is_semantic_brush_from` — expands to a boolean capability query derived from `#[prop(semantic_brush, ..)]` or `#[text_style]`, used to install semantic Environment subscriptions without a code-generator-side property-name list.
- `@clear`/`@clear_from` — resets a property to its declared platform/property default. A semantic `@set_with_environment` arm maps `ResolvedValue::PlatformDefault` here rather than materializing a concrete brush in core.
- `@routed`/`@routed_from` — registers a `#[routed]` callback, building the bubbling adapter around a bare DSL-supplied closure.
- `@attached_set` — a `#[attached]` property's setter, one hop only (no ancestor forwarding — the DSL's `Owner::field` syntax always names the owning class explicitly).
- `@children`/`@children_into` — attaches bare nested child elements to whichever property `#[content(..)]` names, forwarding up the chain until the declaring class is found.
- `@children_erased`/`@children_erased_into` — the same metadata-selected destination for a child that is
  already an `Rc<dyn UIElementExt>` (or another erased content trait). This path calls the declaring
  extension trait with the value unchanged, so cross-crate scalar content does not attempt an
  `into_ui_element_node()` conversion on a trait object. It is a transport detail, not a second
  content model.
- `@content_shape` — selects one of caller-supplied scalar/collection lowering blocks from the
  effective content property's declared shape. Codegen uses this only when an external class has no
  local field table; the decision still comes from `#[content(..)]` metadata and field type.
- `@content_slot_type` — the type-position companion to `@content_shape`, selecting `()` for an
  external scalar content destination and `DynamicChildSlot<T>` for a collection destination. It
  keeps generated storage metadata-driven when the declaring class is outside the codegen crate.
- `@field_type`/`@field_type_from` — expands, in **type position**, to the real Rust type a declared property was given (`elwindui-codegen`'s `resolve_effective_fields`/`synthesize_external_base_fields`, Refs #90: a consumer component that bare-forwards an inherited attribute value from a genuinely external base — `padding: padding` on `#[elwindui::component(inherits Control)]`, dsl_spec.md §3's `ContentControl` pattern — has no local `TypeInfo` to read `padding`'s declared type from, so the synthesized field's own `FieldDef::ty` is instead the literal text `elwindui::core::__elwindui_props_Control!(@field_type padding)`; `generate_view`'s `syn::parse_str::<syn::Type>` already parses an arbitrary type-position macro invocation as an ordinary `syn::Type::Macro`, so this needs no special casing downstream). Same per-property arm/forwarding/terminal-`compile_error!` shape as `@set`, restricted to the same `takes_set_arm`-eligible property set (a routed/attached/collection-content property has no single settable "value type" a struct field could hold).
- `@content_item_dyn`/`@content_field_get` — cross-crate queries backing dynamic (`for`/`if`/`match`) region reconciliation against a content-collection field with no local `TypeInfo`.
- `@assert_undeclared`/`@assert_declared` — compile-time collision/designation probes, emitted in item position next to the class declaration rather than consulted from a use site.

Only `@set`'s `wrap_prop_value` knows how to shape a value into a declared property's real setter; a bare-forwarded field whose own value already carries that exact shape (rather than the bare/literal shape every ordinary call site supplies) is `elwindui-codegen`'s own responsibility to normalize before calling `@set` — see `emit_resync`/`emit_external_attribute_sets`/`build_component_args`'s own `ty.contains('!')` branches in `codegen.rs`.

## Validation boundary

Publicly observable accepted/rejected forms remain in the specification. Parser representation, token generation, registry layout, shadow expansion, and debugging strategy belong only here.

## Generated component shape forwarding across crate boundaries

When `#[component]` generates a Control-derived class, the component code generator re-emits the
component's own public `#[prop]` and `#[content(...)]` declarations into the generated class shape.
The resulting `__elwindui_props_<Name>!` macro is therefore available to a downstream `view!`
expansion through the defining crate root, including property setters, content-shape queries, event
and two-way wiring, and resync. This is shape metadata forwarding; it is not runtime reflection or
a second property system.

The forwarded surface is deliberately limited to public construction/content metadata. Internal
`#[computed]`, `#[state]`, and `#[environment]` values do not become writable external properties.
The external DSL still names the generated component through a qualified Rust path, while the
`#[macro_export]` shape macro is rooted at the defining crate.

`owned` is an internal class-shape flag used only when generated component metadata must preserve an
owned setter convention, for example `#[prop(owned, title: String)]`. It is not recommended
user-facing DSL syntax. The generated shape converts an authored string value to the owned `String`
expected by a generated setter; hand-written builtin declarations retain their existing borrowed
`String`/`&str` setter convention. Non-String owned values retain their declared type without a
String-specific conversion. Direct macro tests cover both cases.
