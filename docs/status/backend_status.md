## AppKit current gaps

- Host-level pointer/keyboard dispatch covers self-drawn elements, including screen-position payloads, drag delivery through release, and exactly-once cancellation for Escape, window/application deactivation, host suppression/detach, tree replacement/clear, and captured-subtree unmount (#179). Native leaves receive OS events directly and require control-specific focus/input wiring. Root/screen conversion is exposed through the common coordinate-host capability (#174).
- Gradient/Image foreground brushes are reduced when a native text widget cannot represent the full brush.
- Editable TextArea character spacing does not cover every native text-storage path.
- Secure PasswordBox intentionally retains the system secure font cascade instead of applying ordinary font synthesis.
- SVG filter replay passes through turbulence, diffuse/specular lighting, displacement maps, unsupported convolve kernels, and Table/Discrete/Gamma component-transfer functions. Group blend modes fall back when no Core Image filter is available.
- SVG nested masks with mismatched bounds use the outer mask only; image-brush path fills, pattern strokes, and degenerate/offscreen patterns use documented simpler fallbacks.
- Memory investigations for Issue #60 found no durable evidence that retained ElwindUI render data directly owns the previously observed multi-megabyte process delta. Raw measurements remain Issue evidence rather than status documents.
- Window's new `hide()`/`close()` (Issue #80 CI-8: `NSWindow::orderOut`/`NSWindow::close`) are implemented and covered by the workspace test suite (constructed, type-checked; interactive on-screen confirmation was attempted but inconclusive in this sandboxed development environment — no crash or early-exit was observed running a real example either before or after the change, but a spawned GUI process's window did not appear in a `screencapture` capture, a pre-existing environment characteristic unrelated to this change).
- Window transparency and floating/normal levels are implemented through `NSWindow`; `mascot-demo` is the focused alpha-image verification surface ([#150](https://github.com/puchinya/elwindui/issues/150)).
- Context Menu & PopupSurface (`#152`): AppKit popup uses owner child window relationship (`addChildWindow:ordered:`) with floating level, dynamic work-area acquisition via `NSScreen.visibleFrame` by anchor, and Core top-left coordinate conversion.
- Context Menu & PopupSurface (`#161`): `InnerPopupSurface::close()` runs `unmount_subtree` on the popup content root synchronously before *any* native detach (event monitor removal may precede it; `removeChildWindow`/`orderOut` and the deferred `TreeHostView::clear_tree()` must not — a review pass caught and fixed an earlier version that ran `unmount_subtree` after `removeChildWindow`/`orderOut`); `close()` also now releases its own strong reference to the content root (`content: RefCell<Option<Rc<..>>>`, taken) rather than retaining it for the surface's remaining lifetime. Verified reentrancy-safe (dismiss triggered from within a popup-internal event handler) and content-release-safe (via a portable `PopupSurfaceHandle` following the same ownership pattern) at the `elwindui-core` level, where both risks live — `unmount_subtree` never touches `TreeHostView`'s own `RefCell`s.
- Declarative `context_popup: view! { .. }` (`#162`): AppKit's `TreeHostView::close_active_popup` now delegates to a free, backend-private `close_active_popup_slot(&RefCell<Option<Rc<dyn PopupSurfaceHandle>>>)` (`take()`-then-`close()`, reentrancy-safe) that backs `Window::unmount_override`, closing the window's own active popup before its content unmounts. `close_active_popup_slot` itself is proven reentrancy-safe and empty-slot-safe by dedicated unit tests that construct only a fake `PopupSurfaceHandle` (no native window needed) and genuinely execute and pass on macOS. `ElwinduiWindow` now overrides `windowShouldClose:` (ivars-based `close_request_handler`) so a native title-bar click/`-performClose:` routes through the same `WindowLifecycleHost::set_close_request_handler` capability a programmatic `WindowExt::close()` reaches — no handler installed means "allow the native default". `NSWindow::close` itself is documented by Apple not to consult `windowShouldClose:`, so the framework's own `Window::close()` never re-enters this override; no reentrancy guard is needed (contrast WinUI 3, below). Compile- and unit-test-verified; the interactive native close-button click itself needs manual verification outside this sandboxed environment (`NSWindow` construction requires the main thread, unavailable in the test harness — see `window_mount_hide_close.rs`'s existing type-check-only convention for AppKit `Window` tests).

## WinUI 3 current gaps

- Self-drawn Canvas pointer pressed/moved/released forwarding, native capture, optional normalized screen positions, and bidirectional root/screen conversion are implemented for #174. Windows verification is pending in Issue #178 and was intentionally separated from PR #175.
- Pointer cancellation/capture-loss handling is implemented for #179 through `PointerCanceled`, `PointerCaptureLost`, host deactivation, tree replacement/clear, and captured-subtree unmount. Windows verification is pending in Issue #180.
- SVG group blend modes without direct `CanvasBlend` mappings, isolation, filters, and luminance-mask rasterization need an offscreen effect graph.
- Cross-backend parity has been verified for the controls recorded in [`control_status.md`](control_status.md), but the entire backend contract has not been re-audited.
- Issue #207's restored WinUI 3 projection/build repairs, callback-lifetime coverage, and the #216 ViewModel codegen boundary fix are integrated for the Windows gate. The integration branch skips absent optional Windows App SDK package roots during bootstrap fallback discovery and preserves public `elwindui::new!` construction in the WinUI lifecycle regression. Shared codegen, core, custom-control, WinUI, macro, and language-server type boundaries produce `Error 0`, `Warning 0`, `E0282 0`, and 196 cfg-only inactive-code WeakWarnings from both repeated `rust-analyzer diagnostics .` runs; non-exempt WeakWarnings are zero. The focused backend check, workspace check/build, `controls-demo` build and runtime launch, Core pointer regression, codegen tests, macro tests, custom-control tests, and the `RUSTFLAGS="--cfg rust_analyzer"` workspace companion pass. The backend suite passes 42/42 and the hosted Button, text/style, Menu, and Window assertions execute when run as the same standard user outside the Codex sandbox; `cargo test --workspace` exits 0, `window_mount_hide_close` passes, and the harness-less `control_template_window_rt4` target completes without E0601. The WinUI3-only `native_ui::Menu::create_flyout` helper is intentionally backend-internal and returns a lifetime-owning realization; this is an approved backend-specific breaking cleanup under Issue #217, with no cross-platform ElwindUI Menu API change and no public raw-native replacement. The original Codex sandbox blocks Windows App Runtime registration with `MddBootstrapInitialize` `0x80070005`; this is an execution-environment restriction, not a reproduced PR #219 bootstrap defect. Issue #215 macOS RT4 execution is an independent post-merge follow-up, not a PR #219 merge blocker.
- Window transparency uses the XAML root's transparent background and topmost state uses `OverlappedPresenter`; Windows runtime verification for Issue #150 remains platform-specific.
- Context Menu & PopupSurface (`#152`): KeyDown context key (Shift+F10 / Apps key), `RightTapped`, and XamlRoot dynamic work-area querying are implemented and unit tested; Windows real-machine GUI runtime verification is tracked in Issue [#157](https://github.com/puchinya/elwindui/issues/157).
- Context Menu & PopupSurface (`#161`): `InnerPopupSurface` splits framework-controlled close from native-originated close — `close()` (programmatic, `PopupDismissAction`, item selection, replacement, `Drop`) runs `unmount_subtree` before `SetIsOpen(false)`/`TreeHostPanel::clear_tree()` (no existing deferred-dispatch workaround on this backend, unlike AppKit); `on_native_closed()` (routed from `Popup.Closed`, native light-dismiss) runs `unmount_subtree` before `clear_tree()` only — it does *not* call `SetIsOpen(false)` again, since WinUI has already performed that transition by the time `Closed` fires (Microsoft's `Popup`/`Popup.Closed` contract: `Closed` is a post-`IsOpen=false` notification, never a pre-close hook — confirmed during Issue #161 review; the portable cross-backend guarantee was corrected accordingly to "`unmount_subtree` before ElwindUI host-tree detach", with WinUI3 native light-dismiss as the one documented native-visibility exception, see `docs/design/runtime/popup_context_menu_design.md` §6/§7). Both paths share one exactly-once `begin_close` guard and both release their own strong `content` reference (`RefCell<Option<Rc<..>>>`, taken). `InnerPopupSurface::show()` propagates every structural native setup failure (coordinate conversion, `Popup::new`, casts, every `FrameworkElement`/`Popup` property setter, `Closed` handler registration, `SetIsOpen(true)`) as `None` instead of discarding them with `.ok()` — a review pass found `SetIsOpen(true)`'s own failure was previously silently ignored, so a popup could fail to actually open while `show()` still reported success. `request.content` is not attached (`set_tree`) until all of that succeeds, so a late failure never needs to detach already-attached content. `WinUI3PopupHost::show_popup` returns `None` on any of this instead of a handle wrapping a `None` inner surface — the caller unmounts the already-built content in that case. Code-reviewed only, not yet exercised on Windows hardware (this crate is `#![cfg(target_os = "windows")]`-gated and does not compile on macOS at all, so not even `cargo check` was possible here) — folded into the [#157](https://github.com/puchinya/elwindui/issues/157) runtime verification backlog.
- Declarative `context_popup: view! { .. }` (`#162`): `TreeHostPanel::close_active_popup` delegates to the same `close_active_popup_slot` free-function shape as AppKit's (`take()`-then-`close()`); its unit tests exist in this crate but this crate is `#![cfg(target_os = "windows")]`-gated, so they are NOT VERIFIED on this macOS development machine, unlike the AppKit equivalents. `close_active_popup_slot` backs `Window::unmount_override`. `InnerWindow::try_register_closing_handler` registers `AppWindow.Closing` (Windows App SDK 1.3+) at most once — retried from `show()` in case `AppWindow` isn't available yet at construction. On a native close attempt it does not unconditionally cancel: `framework_initiated_close` being set (our own `InnerWindow::close`'s `xaml.Close()` triggered this `Closing` event) allows the native close to proceed without ever consulting the handler; otherwise, if no handler is installed, the native default close is also allowed; otherwise the installed `close_request_handler` (`WindowLifecycleHost::set_close_request_handler`) is invoked and its return value decides — `true` means the framework accepted the close and is now handling it through the generated `WindowExt::close()`, so the native attempt is cancelled (`AppWindowClosingEventArgs::SetCancel(true)`); `false` means the generated owner is already gone, so the native default close is allowed to proceed uncancelled (PR #165 review remediation, A1 — the same bool contract AppKit's `should_allow_native_close` implements). Unlike AppKit's `windowShouldClose:`, `AppWindow.Closing` fires for *any* close including the framework's own (`InnerWindow::close`'s `xaml.Close()`), so the `framework_initiated_close: Rc<Cell<bool>>` guard (set for the duration of that call, shared with the registered handler closure) is what suppresses the handler from re-triggering on our own close. Code-reviewed only; this crate is `#![cfg(target_os = "windows")]`-gated and does not compile on macOS, and cross-compiling to `aarch64-pc-windows-msvc` in this environment fails (target triple metadata present, full std/core artifacts not installed) — not even `cargo check` was possible here. Folded into the [#157](https://github.com/puchinya/elwindui/issues/157) runtime verification backlog.
